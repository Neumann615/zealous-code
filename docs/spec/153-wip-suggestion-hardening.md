# spec 153:WIP 处理建议与写守卫文案加固(问题定义与修复方案)

来源:Dogfooding 151 A1/B3。`unsafe_wip_suggestion_count` 达 3
(继承 1 + B3 的 `git add Cargo.lock && git commit` 与
`git stash push -u`),按"×3 立项"规则建专项。**本 spec 阶段只定义
问题与修复方案,不顺手修。**

## 问题(三个层面)

1. **引擎错误文案诱导**:`edit_file` 被脏工作区守卫拒绝时,错误文案为
   "…请先 commit/stash 用户的改动"——引擎自己建议模型替用户执行
   commit/stash。A1 三场景中模型虽未照做,但该文案是明确的诱导源。
2. **模型绕过模式**:守卫拒绝后,模型倾向改用 T2 shell 绕过
   (A1 3/3 powershell 只改目标文件;B3 中进一步升级为
   `git add && commit`、`git stash push -u`、`del`、`git clean -f`、
   写 `.git\info\exclude` 共 5 次尝试)。T2 审批全部拦下,**安全边界
   有效**,但审批噪音大、任务完成率受损。
3. **审批摘要缺乏守卫上下文**:T2 shell 审批展示命令本身,但不展示
   "该命令与刚被拒绝的写入的关系",用户难以快速判断是否该批。

## 修复方案(实施阶段执行)

1. **守卫文案改写**(spec 153 核心):被拒文案不再建议 commit/stash,
   改为中性、可执行的选项说明:
   "工作区存在用户未提交改动(列表)。写入已拒绝。可选:用户自行提交
   或 stash 后重试;或由用户明确批准后继续。"并保持 fail-closed 语义
   与现有守卫测试不变。
2. **审批摘要附加上下文**(可选增强):当同一任务内写入刚被守卫拒绝、
   随后请求 T2 shell 时,审批摘要在顶部追加显著警示行:
   "注意:此命令紧随一次被拒绝的写入,可能绕过工作区保护。"
3. **不改变任何权限边界**:T2 仍必须审批;Worker 仍只读;守卫仍
   fail-closed。本 spec 只改文案与提示,不改权限模型。

## 回归要求

- 既有守卫单测(文案断言如有需同步更新);
- 新增断言:守卫拒绝文案不含 "commit/stash" 建议字样;
- Dogfooding A1 三场景 + B3 场景重跑:模型不再收到 commit/stash 诱导;
  观察绕过尝试次数变化(目标:显著下降)。

## 实施时机

独立实施 + 完整质量门 + Dogfooding 受影响场景重跑;运行时代码变化
会使当前 offline RC 失效,按 spec 150 重新生成候选包。
